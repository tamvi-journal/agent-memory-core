# R0: frozen semantics for the identity port (Python oracle → Node 22 / TypeScript)

**Date:** 2026-09-30
**Settlement it implements:** Lam, "Runtime settlement for Trajecta product" (2026-09-30): one production runtime, Node 22 / TypeScript, for Work and Identity. The port is a semantic port: freeze semantics first, port after. Sequence R0 → R1 → R2 → R3 → R4.
**Status:** settled by Lam (Q1–Q6, F1–F3, 2026-09-30). The settlement is recorded at the end; the sections below follow it.
**Oracle:** this repo at `def576d` (`memory_core` + `trajecta_identity`, 86 tests).

## 0. What R0 freezes, and how parity is judged

- The Python code at `def576d` is the **oracle**. It stays in the repo and in CI until R4.
- This document states the contract in language-independent terms. Where the Python code and this document disagree, the disagreement is a bug to settle. It is never decided silently by the port.
- The **golden corpus** (§9) is generated by the oracle and checked into the repo. The TS runtime passes R1/R2 only when it reproduces the corpus exactly, except where §9.4 names a tolerance.
- **Deterministic by construction.** Every clock and id source is injected (§3). The corpus is generated with a fixed clock and `PYTHONHASHSEED=0`.
- Any behaviour that exists only in Python code, and not in this document or the corpus, blocks the retirement of the Python writer (Lam's definition of done).

## 1. Storage: on-disk format is the contract

- **Engine.** SQLite, the same file format. TS uses `node:sqlite` (`DatabaseSync`), with no native addon and no WAL substitute. TWM's JSONL journal is **not** used for identity. From Work, identity reuses only the idea of one writer per store and settled reads, not its files.
- **Schema.** `memory_core/schema.sql` is used **verbatim**. It is copied byte-for-byte into the TS package and checked by digest in CI.
  - `APPLICATION_ID = 0x414D4333` ("AMC3").
  - `SCHEMA_VERSION = 4`; the legacy version is 3.
  - `EVIDENCE_IDENTITY_VERSION = "evidence-v2"`.
- **Connection pragmas.**
  - `foreign_keys=ON` on every connection.
  - **Journal mode is asserted, not assumed (F2).** The declared mode is `DELETE`. A persisted mode can differ in an existing file (WAL is stored in the header), so:
    - on a writable open, the runtime reads `PRAGMA journal_mode`; if it is not `delete`, it sets `PRAGMA journal_mode=DELETE` deliberately and verifies the result, failing closed if SQLite refuses;
    - on a read-only open, a persisted `wal` mode, or a `-wal`/`-shm` sidecar next to the file, fails closed with a typed error (`IncompatibleJournalMode`) that names the explicit repair command. Read paths never convert;
    - the oracle gets the same check, shipped with P3's PR as a fail-closed guard that changes no stored data.
  - Busy timeout is 5000 ms, matching Python's `sqlite3.connect` default.
- **Opening rules** (same as the oracle):
  - A read never creates, initializes or migrates a store. A missing file reads as empty.
  - Opening fails closed on these stores:
    - a foreign `application_id`;
    - a `user_version` above 4 (a future store);
    - an uninitialized database.
  - A v3 store raises `MigrationRequired`. Migration is an explicit command that works on a copy (`migrate_to(target)`).
  - Read-only connections use `mode=ro` URIs.
- **Transactions.**
  - Every mutation runs in one transaction.
  - Python uses a deferred `BEGIN` through `with conn:`. TS uses `BEGIN IMMEDIATE` (Q4).
  - The contract is atomicity, no partial write, no lost update, and fail-closed. Lock-acquisition timing is implementation behaviour, not semantic parity: TS may fail earlier under contention. Write conformance compares committed and rejected outcomes under controlled fixtures, never wait durations.
  - Retrieval with tracking is **not** one transaction: each access row is its own write. This is frozen as is.
- **Immutability is enforced by triggers**, not by the runtime:
  - records, revisions, evidence and revision-evidence links: no update, no delete;
  - lifecycle events and relation events: append-only;
  - the lifecycle owner guard and current guard apply.

  The TS runtime must not attempt statements that the triggers reject. R2 negative tests assert that the triggers fire.
- **Views are the read API:** `memory_current_v3`, `memory_revision_state_v3`, `memory_relation_current_v4`. The TS runtime reads through the views and never recomputes "current" in code.
- **Sidecar files.** The decay state lives in `<db stem>.activation.json`, holding `{"last_decay_at": iso}`. It is found via Python's `with_suffix`: for example, `aux_.sqlite3` → `aux_.activation.json`.
- **Paths** follow `trajecta_identity/paths.py` exactly:
  - data directories per OS;
  - `safe_fs_name`, including the Windows reserved names;
  - the profile search order;
  - `TRAJECTA_IDENTITY_DATA_DIR`, `TRAJECTA_IDENTITY_PROFILES`, `TRAJECTA_WORK_ROOT`.

## 2. Query order (total orders only)

Every list the runtime returns has a total order. SQLite `BINARY` collation equals code-point order on UTF-8.

| Read | Order |
|---|---|
| `current_view()` | `domain, record_id` |
| `historical_view(id)` | `revision_number` |

## 3. Clock and identifiers

- `utc_now()` returns `YYYY-MM-DDTHH:MM:SS+00:00`: seconds precision with a `+00:00` suffix, never `Z`.
- The recall maintenance `run_id` uses microsecond precision: `recall:YYYY-MM-DDTHH:MM:SS.ffffff+00:00`.
- Decay `moment.isoformat()` uses Python's default format: microseconds appear **only when they are non-zero**. The TS runtime reproduces that rule.
- Clock and id sources are injected everywhere, in both runtimes, for the corpus.
- **Deterministic ids** (hex is lowercase sha256):
  - `revision_id = "{record_id}@r{n}-" + sha256(idempotency_key)[:12]`
  - `operation_id = "operation:" + sha256(key)[:32]`
  - `lifecycle_id = "lifecycle:" + sha256("{key}:lifecycle:{state}")[:32]`
  - `evidence_id = "evidence:{identity_version}:" + evidence_sha256[:32]`
  - `relation_event_id = "relation-event:" + sha256(key)[:32]`
  - Stable relation id: `"relation:" + hash_payload([from, to, type])[:32]`. The identity layer passes its own `relation_id = "{from}->{type}->{to}"`. Both forms are frozen as the oracle uses them.
  - `record_access.cue_sha256 = sha256(utf8(cue))`.
- **Identity-layer keys** (`trajecta_identity/identity.py`):
  - `_digest(*parts)` = `sha256(json.dumps(parts, ensure_ascii=False, sort_keys=True, default=str))[:16]`. The separators are the **defaults** `", "` and `": "`, not the compact ones. This is a second canonical form, and it is frozen.
  - Anchor keys: `{profile}:{anchor}:v1`.
  - Core seed: `{profile}:core:seed:v1`.
  - Phase: `{profile}:phase:{event_id}`.
  - Fact: `{profile}:fact:{id}:{_digest(title, summary, content, confidence)}`.
  - Core revision: `{profile}:core:{_digest(core_content, reason)}`.
  - VHO seed: `vho-open-ontology-core:{VHO_VERSION}:{adoption}`.
  - Retract: `{profile}:retract:{record_id}:{utc_now()}`. This key is clock-bound, so a retry a second later is a new operation. That is a known gap (G5).

## 4. Canonical encodings

### 4.1 `hash_payload` (compact canonical JSON)

The byte string is exactly what Python produces with `json.dumps(v, ensure_ascii=False, sort_keys=True, separators=(",", ":"))`, encoded as UTF-8.

- Object keys are sorted **by code point**.
- Strings:
  - escape `"` and `\` as `\"` and `\\`;
  - escape `\n \r \t \b \f` as those short forms;
  - escape other U+0000–U+001F as `\u00xx`, with lowercase hex;
  - leave everything else raw, including U+007F, U+2028 and U+2029.
- Lone surrogates are **rejected** at input. Python fails when it encodes them; JS would escape them.
- `true`, `false` and `null` are literal.
- `NaN` and `Infinity` are **rejected**. Python would emit them, but no stored value may contain them.
- `default=str` is not part of the contract: only JSON types reach the hash.

### 4.2 Numbers: `py_float_repr` and typed values

- A value is either an **int** or a **float**. The kind is part of the value, because Python hashes `1` and `1.0` differently.
- An int renders as a decimal integer.
- A float renders as Python's `repr(float)`:
  - Use the shortest round-trip digits (both runtimes produce the same digits).
  - If the decimal exponent is below −4 or at least 16, render `d[.ddd]e±XX`, with the sign always present and at least two exponent digits.
  - Otherwise render fixed-point, with `.0` appended when the value is integral.
- Fields the oracle always coerces to float are floats regardless of input: `confidence` in `semantic_hash`, `weight`, telemetry, `old_value`/`new_value`. The TS types mark them.

### 4.3 Input JSON is parsed losslessly

MCP arguments and profile files reach hashes and stored content (the governance `proposal_sha256`, `phase_context`, `core_content`). So the TS runtime parses input JSON with a parser that:

1. keeps object key order as written, including integer-like keys;
2. keeps the number kind: a token with `.`, `e` or `E` is a float, otherwise an int.

The parser returns an **ordered-entry AST**: objects are arrays of `[key, value]` entries, and numbers carry their lexical kind and text. It never materializes a plain JS object, because a JS `Record` enumerates integer-like keys first and cannot keep insertion order.

**Where it runs (F1).** Order and number kind are lost the moment `JSON.parse` runs, and they cannot be recovered afterwards. So:

- The TS MCP transport reads each raw JSON-RPC line and parses it with the lossless parser **before** any ordinary object is built. Tool arguments that reach a hash or stored content are passed on as AST values. If a standard MCP SDK would run `JSON.parse` on the line first, it is not used for these tools, because parity is impossible behind it.
- Profile files (`profile.json`, including the core seed and `phase_context`), and any other JSON whose key order or number kind reaches a hash or stored content, are read with the same parser.
- `JSON.parse` is allowed only for values proven not to reach a hash or stored content (for example `limit`, `budget`, `include_history`).

Other encodings:

- **`core_content`** = `json.dumps(obj, ensure_ascii=False, indent=1)`, without `sort_keys`.
  - The top-level key order is `vho_stack`, `recognition_signature`, `falsifier`, `phase_context`.
  - `vho_stack` follows `VHO_KEYS` order.
  - `phase_context` keeps its input order.
  - Indent-mode separators are `","` plus a newline and `": "`.
- **`_compose`** writes `phase_context` with `sort_keys=True` and default separators.

### 4.4 `py_fixed(x, d)`: fixed-point formatting

`py_fixed(x, d)` is Python's `format(x, f".{d}f")`: round the **exact** binary value to `d` digits, ties to even. It is used in these places:

- `lexical:{overlap:.2f}` and `title:{…:.2f}` in retrieval reasons;
- `confidence: {:.2f}` in packets;
- `round(v, 6)` in activation and decay. `round` uses the same exact half-even rule, and returns a float.

The TS implementation expands the double exactly (with BigInt) and rounds half to even. `toFixed` and `Math.round` are not allowed.

### 4.5 Slices and lengths

Every `[:n]` in the oracle is a code-point slice:

- cue `[:240]`;
- summary `[:350]` in packets;
- `[:300]` in evidence and relation reasons.

`len(p) > 1` in `tokens()` applies to ASCII tokens only, so it is the same in any unit. The packet estimate counts UTF-8 bytes (§6.5).

### 4.6 Whitespace split (`str.split()`)

The split runs on maximal runs of this set, and empty fields are dropped:

- U+0009–U+000D;
- U+001C–U+001F;
- U+0020, U+0085, U+00A0, U+1680;
- U+2000–U+200A;
- U+2028, U+2029, U+202F, U+205F, U+3000.

U+FEFF and U+200B are **not** whitespace.

## 5. Text normalization, defined by a frozen table

The oracle's functions:

```
normalize_text(v)        = join(" ", findall("[a-z0-9_]+", fold(casefold(v).translate(T))))   # text-norm/v2
normalize_identity_v1(v) = join(" ", findall("[a-z0-9_]+", fold(casefold(v))))                # frozen, evidence ids
fold(s)  = drop code points with canonical combining class ≠ 0 from NFKD(s)
T        = đ→d ð→d ł→l ø→o ħ→h ı→i ŧ→t æ→ae œ→oe þ→th
tokens(v) = [p for p in normalize_text(v).split(" ") if len(p) > 1]
```

**Every step is per code point.**

- Python's `casefold` is context-free full case folding.
- `translate` works per character.
- NFKD reordering only moves marks with ccc ≠ 0, and those are all dropped.

So the whole function is `concat(M(c) for c in v)` for a per-code-point map `M`, followed by the token regex. `M(c)` is a string over `[a-z0-9_]` plus a separator.

**Contract:** text-norm/v2 and identity-v1 are **defined by tables generated once from the oracle** on Python 3.11 (Unicode 14.0.0). These are `memory_core/tables/text-norm-v2.json` and `memory_core/tables/identity-v1.json`. They are package data next to `schema.sql`, so every install carries them, including the vendored Claude `.plugin`.

- Each table stores only the code points that do not map to "separator":
  - `c → "tokenchars"`, for example `ễ → "e"` and `𝐀 → "a"`;
  - `c → ""` for a code point that is dropped and so joins its neighbours, for example U+0301;
  - `c → "a b"` for a code point whose mapping contains an internal separator, for example `¼ → "1 4"`;
  - separators at either **end** of the mapping are kept as a space, because they split the code point from its neighbours: `⑴ → " 1 "`, so `a⑴b` normalizes to `a 1 b`, not `a1b`. In general the value is the exact per-code-point output with every run of non-token characters written as one space (found by Codex in R0b).
- Every code point not in the table is a separator.
- Surrogates are excluded, because lone surrogates are rejected at input.
- **Table format and integrity.** Each table file is `{"schema": "trajecta.norm-table/v1", "name": "text-norm/v2" | "identity-v1", "unicode": "14.0.0", "generator": {...}, "map": {"<hex code point>": "<output>"}}`. Its sha256 is recorded in `spec/golden/MANIFEST.json` and pinned as a constant in both runtimes. Each runtime verifies the digest when it loads the table and refuses to start on a mismatch.
- **Both runtimes use the table.** Oracle patch P3 makes the Python functions table-driven, so Python 3.10 / 3.13 CI stops drifting (H9).
- A code point whose mapping differs between Unicode 13, 14, 15.1 and 17 is listed in `memory_core/tables/version-sensitive.json` for review. The frozen table wins.
- The version string stays `text-norm/v2`, and stored `cue_norm` values are unchanged:
  - the oracle recomputes `cue_norm` from the raw cue at query time;
  - for every code point that exists in Unicode 14, the table is identical to Python 3.11.
- Any future change is `text-norm/v3`, with the same recompute-at-read rule.

## 6. Recall: exact algorithm and order

### 6.1 Candidates

The candidates are the rows of `current_view()` in §2 order, filtered to:

- `authority_status != non_authoritative`;
- `record_class != unclassified`;
- `scope ∈ {global, scope}`.

The candidates are keyed by `record_id`, in that iteration order. Every candidate starts with score 0.0 and an empty list of reasons.

**Dormancy** is off unless `min_accessibility` is set. When it is set:

- a candidate whose accessibility is below `min_accessibility` is dormant;
- bootstrap ids are never dormant.

### 6.2 Cues

1. **Build the list.** Take the stored `cue_rows` (§2 order). For each one, recompute `cue_norm` from the raw cue. Append the profile `cue_aliases` in declared order.
2. **Keep the strongest.** For each `(cue_norm, target)` pair, keep the cue with the highest weight. On a tie, the **first** one wins, because the comparison is strictly `>`.
3. **Match.** Walk the kept cues in first-insertion order. For each cue whose target is a candidate, and that is not dormant (or `wake_on_direct_cue` is set):
   - `exact` = the cue's `cue_norm` is non-empty and is a **substring** of `normalize_text(query)`. This is a string containment test, not a token test.
   - `overlap` = |query_tokens ∩ cue_tokens| / max(1, |cue_tokens|).
   - The cue matches when `exact` is true or `overlap ≥ 0.8`.
4. **On a match:**
   - `gain = weight × (1.45 if exact else 0.9 × overlap)`;
   - a dormant target wakes, with reason `woke:direct-cue`;
   - `score += gain`;
   - add reason `cue:{raw cue}`;
   - the target joins `direct`.

### 6.3 Lexical and title

For each candidate in iteration order that is not dormant:

- `M` = tokens of `title + "\n" + summary + "\n" + content`.
- When both the query tokens and `M` are non-empty:
  - `ov` = |Q ∩ M| / max(1, |Q|). If `ov` > 0, then `score += min(1, ov) × 0.9` and add reason `lexical:{py_fixed(ov, 2)}`.
  - `tov` = |Q ∩ tokens(title)| / max(1, |Q|). If `tov` > 0, then `score += min(1, tov) × 0.6` and add reason `title:{py_fixed(tov, 2)}`.

  The title term applies only when `M` is non-empty.
- **Bootstrap:** each bootstrap id that is a candidate gets `+0.34` and reason `bootstrap`, in profile order.

### 6.4 Graph spread

- The frontier starts as `{id: score[id] for id in sorted(direct)}` (P1: **sorted by code point**).
- For each depth 1 and 2, iterate the frontier in insertion order, and for each frontier entry iterate the relations in §2 order:
  - The relation touches the source in either direction, and the other end is a candidate.
  - A dormant other end continues only if the relation type is in `wake_relation_types`. In that case it wakes, with reason `woke:relation:{type}`.
  - `gain = activation × weight × F[depth]`, with `F[1] = 0.46` and `F[2] = 0.46 × 0.46` computed as a product. If `gain < 0.05`, skip.
  - `score += gain`; add reason `graph:{src}-[{type}]->{tgt}:d{depth}`.
  - `next[tgt] = max(next[tgt], gain)`. Insertion order is first touch.
- **Telemetry term.** For each candidate with score > 0 that is not dormant, add these four terms **in this order**: `confidence×0.28`, `salience×0.14`, `stability×0.12`, `accessibility×0.08`.

### 6.5 Rank, select, track

- **Rank:** keep candidates with score ≥ 0.24 that are not dormant. Sort by `(-score, record_id)`. The float comparison is exact and the string comparison is by code point.
- **History:** `include_history` if it is given. Otherwise history is on when any `normalize_text(marker)` is a substring of the normalized query.
- **Select**, walking the ranked list:
  - `estimate = max(1, 2 × len(split(title + summary + content)))`, using §4.6 split and plain concatenation;
  - if `selected` is non-empty and `spent + estimate > token_budget`, **skip** the hit (continue, not break);
  - if `len(selected) ≥ limit`, **break**.
- **Track** (only when `track_access`): after each selection, call `record_access` with:
  - `rank` = the 1-based position;
  - `retrieval_reason` = the first 5 reasons joined with `,`;
  - `gain` = `access_gain`.

  Telemetry update: `accessibility = MIN(1.0, acc + gain)`, `access_count + 1`, and `last_accessed_at = updated_at = utc_now()`.

### 6.6 Packet renderer (`memory_core/packet.py`)

- The estimate is `max(1, ceil(utf8_bytes(text) / 4))`, version `deterministic-utf8-quarter/v1`. A budget below 64 is refused.
- The line layout is fixed as in the oracle. `Generated:` comes from the injected clock.
- **Budget check.** Framing plus instructions over budget is an error. Otherwise the renderer adds hits greedily: each hit is kept if the whole packet still fits, otherwise it is skipped.
- **Join:** `"\n".join(lines).strip() + "\n"`. Python `strip()` removes whitespace per its own definition, so the TS runtime uses the §4.6 set plus Python's `str.strip` set, which is the same.
- **Sections:**
  - follow the profile `section_order`, then any other domains sorted by code point;
  - the label is the profile label, or the domain with `_` replaced by a space and title-cased by Python `str.title()` (the corpus pins this for the ASCII domains in use).
- **Hit block:**
  - the heading is the title;
  - the next line is `summary`, or `content[:350]` when the summary is empty;
  - in non-compact mode, the content follows when it differs from the summary;
  - then the id line, with `confidence: {py_fixed(c, 2)}`;
  - then `retrieval:`, with the first 5 reasons;
  - then history lines, when history is on.

### 6.7 Identity packet (`IdentityMemory.retrieve`)

- **Call.** It calls the retriever with:
  - `token_budget = max(8 × budget, 20000)`;
  - `min_accessibility = 0.15`;
  - `wake_relation_types` = `later-phase-of`, `caused-by`, `depends-on`, `decided-because`;
  - `access_gain = 0`.
- **Pinned records.** If `core` or `vho-open-ontology-core` is not among the hits, it is appended with score 0.0 and reason `pinned`, core first.
- **Stable partition.** Pinned ids come first; the order is otherwise unchanged. The pinned set is `core`, `vho-open-ontology-core`, `anchor:discussions`, `anchor:open-loops`.
- **Recall adjustment** (only when `track`):
  - A non-pinned hit is direct when any reason starts with `cue:` or `lexical:`.
  - `gain(v, g, cap) = v ≥ cap ? cap : min(cap, v + g × (1 − v/cap))`, where `g` is 0.08 for a direct hit and 0.03 otherwise, and `cap = 0.9`.
  - A hit with a `woke:` reason gets `max(new, 0.4)`.
  - The adjustment is recorded when `|new − v| > 1e-9`, with `round6(new)`.
  - All adjustments go into **one** `apply_maintenance`, with `run_id = recall:{µs iso}`.
- **Packet output:** `schema: trajecta-identity-packet/v1`. The field order is as in the oracle.
  - `self_authored` is true when every evidence item of the revision is `self_log`.
  - `self_authored_share = round(count / n, 2)`, using Python `round`, half-even on exact values.
  - `causal_neighbors`, `open_discussions` and `open_loops` are built as in the oracle.

## 7. Write laws (R2)

These are frozen from the oracle. R2 ports them exactly; the gaps in §7.6 are fixed only after parity, and in both runtimes.

### 7.1 Kernel

**`create_current`, `revise`, `invalidate`.**

- Revision operation types are `correct`, `refine` and `supersede`. They carry semantic fields plus telemetry only.
- An idempotency replay returns the prior result **without comparing the input**. This is gap G1.

**`semantic_hash`.** It covers `{title, summary, content, impact, confidence: float, authority_status}`. Missing values default to `""`, 0.7 and `canonical_reference`.

**`add_cue`.** It upserts on `(profile, cue_norm, target)`. Cues are mutable (G4).

**Relations.**

- `add_relation` and `retract_relation` append events.
- A no-op is when the state is unchanged, meaning weight within 1e-9 and the same source revision.
- The weight must be in [0, 10], and `from != to`.

**`record_access`.** The gain must be in [0, 1].

**`apply_maintenance`.**

- The fields are limited to salience, stability and accessibility.
- `old_value` must match within 1e-6.
- `new_value` is clamped to [0, 1].
- A change within 1e-9 is skipped.
- The semantic hash is re-verified before the commit.
- The operation key is `maintenance:{run_id}`.
- It returns a no-op result when nothing applied.

### 7.2 Governance (`ValidatedIntake`)

**Thresholds.** Confidence floors are event 0.6, belief 0.7, axis 0.75. An axis also needs 2 independence groups and a falsifier. Protected domains: `boundary`.

**Idempotency.** A reused key with a different `proposal_sha256` is refused. This check is not atomic across connections (G2).

**Decisions.**

- No-op when the semantic hash is unchanged.
- Hold on any of:
  - protected weakening;
  - a protected revision without a safe effect;
  - an unresolved conflict;
  - low confidence;
  - an axis without a falsifier or without independence.

**Owner authority.** `protected_authorized` is a caller boolean. This is gap G3.

**The identity layer uses `SELF_AUTHORED_POLICY`:** all floors are 0, one independent source is enough, and there are no protected domains.

### 7.3 Identity write law (SPEC §1)

- **Phase:** `phase:{id}`. Create only; a repeat returns `exists`. Links are checked to exist. Work refs are checked against the linked TWM store, which is read-only. Cues include the title.
- **Fact:** `fact:{id}`. Unchanged (title, summary, content) → `no_op`, with links still applied. Otherwise `create`/`refine`, and the history is kept.
- **Core (legacy v0.1, frozen only for the read oracle):** `revise_core` requires a reason and a non-empty `phase_context`, and the merged core must pass `validate_core`. On `materialized`, it adds the relation `core → anchor:discussions` of type `awaiting-discussion`, with `source_revision_id` set to the new revision. **This writer is not ported.** R2 replaces it with authority-v2 (§7.5) in both runtimes.
- `close_discussion` and `close_loop` retract a relation. In authority-v2, free-form `close_discussion` no longer settles a core proposal; see §7.5.
- `retract` invalidates a record. Pinned ids are refused. In authority-v2 it is gated by an owner receipt.

### 7.4 Activation and decay

**Policy.** `new_record` 0.6, `dormant_below` 0.15, `fading_below` 0.35, cap 0.9, direct gain 0.08, graph gain 0.03, `wake_to` 0.4, half-life 21 days.

**Decay.** Records that are pinned or in the `anchor` domain are skipped.

- `since` is the maximum of the last run, `last_accessed_at` and `created_at`.
- `half_life = 21 × (0.5 + stability)`.
- `new = min(cap, v × 0.5^(days / half_life))`.
- The adjustment is recorded when `|Δ| > 1e-6`, with `round6`.
- The sidecar file is written after the maintenance.

**Ego guard.** Recall never touches stability.

### 7.5 Authority-v2 (settled Q3; introduced at the start of R2 in both runtimes)

This intentionally changes SPEC §1. **Self-authored** means the agent authors the proposed self-location. **Authority** means who may change the canonical core revision. The agent never needs permission to write a proposal; a proposal never becomes the canonical core before an owner receipt.

- **A1 — Append-only history.** Revisions, evidence, lifecycle events, relation events, proposals and receipts are append-only. Triggers enforce this, and negative tests prove that each trigger fires from TS.
- **A2 — `identity_core_propose` (agent, MCP).** It appends a core proposal and opens its discussion. The proposal binds:
  - `baseCoreRevisionId`, the current core revision;
  - `contentDigest`, the sha256 of the would-be `core_content`;
  - `phaseContextDigest` and `reasonDigest`;
  - `proposalId` and `proposalDigest`, the digest of the whole proposal.

  The current core does not change. Open proposals surface in every packet, as `open_discussions` does today, until they are decided.
- **A3 — Owner decision (CLI only).** The owner CLI issues a typed receipt, purpose `identity_core_revision`. It binds at least `{profile, currentCoreRevisionId, proposalId, proposalDigest, contentDigest, phaseContextDigest, reasonDigest, outcome, authority: "owner"}`, where `outcome` is `apply` or `reject`.
  - No MCP tool issues receipts.
  - The fabricated actor string `"{agent}+{owner}"` is removed.
- **A4 — `identity_core_apply` consumes the exact receipt**, in **one** SQLite transaction:
  1. re-check that the current core revision equals the receipt's `currentCoreRevisionId`, and that the proposal is still open;
  2. for `apply`, materialize the new core revision from the proposal's content;
  3. settle that exact proposal and its discussion as applied or rejected.

  A `reject` receipt settles the proposal with no core mutation. Free-form `close_discussion` is not overloaded for either outcome.
- **A5 — `identity_retract`** is gated by an owner receipt, purpose `identity_retract`, bound to `{profile, recordId, currentRevisionId, reasonDigest}`.
- **A6 — No silent promotion.**
  - `core` and `vho-open-ontology-core` are written only by bootstrap (`skip_if_exists`) and by `identity_core_apply`.
  - Anchors are written only by bootstrap.
  - No generic submit reaches a pinned id.

  Negative tests cover a fact id or phase id equal to a pinned id, and a raw submit to `core`.
- **A7 — A retry is not new authority.**
  - A receipt dies when the current core revision or the proposal's state changes.
  - Replaying the same operation with the same receipt is idempotent: it returns the prior result and grants nothing new.
  - A receipt of one purpose never authorizes another.
- **Fixtures.** Authority-v2 gets its own write scenarios and corpus in `spec/golden-authority-v2/`. They are generated by the Python writer once it has authority-v2, and the TS writer is compared against them. The legacy read corpus (§9) is not regenerated for this.

## 9. Golden corpus

### 9.1 Generator

`tools/golden/generate.py` runs the oracle with:

- `PYTHONHASHSEED=0`;
- an injected clock: a fixed start that advances 1 s per call, with a separate µs clock for run ids;
- temporary data directories.

For each scenario it writes `spec/golden/<scenario>/`:

- `store.sqlite3`, the final store as the oracle wrote it;
- `dump.json`, every table in primary-key order, with floats written as `py_float_repr` **and** hex (`float.hex`);
- `cases.jsonl`, one query per line, each with:
  - its input;
  - `current_view` or `historical_view` rows;
  - ranked hits, with `record_id`, score as hex, and reasons;
  - the selected hits;
  - the packet text;
  - the identity packet JSON;
  - the status, timeline, open discussions and open loops.

`spec/golden/MANIFEST.json` holds:

- the sha256 of every file, including the two normalizer tables;
- the oracle commit;
- the Python version, the Unicode version and Python's `sqlite3.sqlite_version`;
- for conformance runs, the Node version and the `node:sqlite` SQLite version.

**Determinism proof (F3).** `PYTHONHASHSEED=0` is the canonical generator setting, not the proof. CI regenerates the whole corpus under seeds 0, 1 and 4294967295, and asserts that every run is byte-identical to the checked-in corpus. Any difference fails CI, because it means hidden set-order non-determinism survived P1–P3. CI also fails on any diff against the checked-in corpus on Python 3.11.

### 9.2 Scenarios (minimum)

**Text**

- Vietnamese: `Tâm Vi`, `đường`, `ươ`, all five tone marks, in NFC and NFD, mixed.
- `casefold` versus lower: `ß`, `ẞ`, `ſ`, `İ`, `ς`, `ﬁ`.
- Fullwidth characters, math alphanumerics, `¼`, `²`, `™`.
- Non-Latin text: CJK, Cyrillic, Arabic, Thai, which become separators.
- Emoji and astral characters in cues, titles and slices.
- One-character words.
- Whitespace edge cases: U+0085, U+001C, U+FEFF, U+200B, U+3000.

**Recall**

- Exact cue versus overlap at exactly 0.8.
- Two cue rows with the same key and equal weight.
- Alias versus stored cue.
- `lexical` and `title` ties at 1/8, 3/8, 5/8 and 7/8 (H2).
- Equal scores, where the order comes from the `record_id` tie-break, including non-ASCII ids.
- Graph at depths 1 and 2, with multiple sources converging on one target (H1), bidirectional edges, and a gain just under 0.05.
- Dormant records that wake through a direct cue and through a causal edge; a dormant record reached through a non-wake edge.
- History triggered by a marker; `include_history` false and true.
- Budget: skip versus break; the first hit over budget; the limit reached.

**Packet**

- Budget exactly at the framing limit; a budget of 64; UTF-8-heavy text.
- Pinned core and ontology past the limit.
- Unknown domain sections.

**Identity**

- Bootstrap, then a phase chain with `follows`, `caused_by` and `open_loop`.
- A fact that is created, gets a no-op, and is then refined.
- `revise_core`, then an open discussion, then close.
- Retract.
- Recall adjustments: direct, graph, wake and cap.
- Decay at 0, 7, 21 and 400 days with different stability values.
- Decay boundary fixtures (Q6):
  - accessibility landing just above and just below 0.15 and 0.35;
  - values at and around the 0.9 cap;
  - a maintenance change of exactly 1e-6, and on each side of it.

**Encoding**

- `phase_context` with integer-like keys and key order (H5).
- `1` versus `1.0` in a proposal (H6).
- Floats `1e-05` and `1e16` (H3).
- Keys that need code-point sort (H4).

**Stores**

- A legacy v3 store, which must raise `MigrationRequired` and must not be modified (compare its bytes).
- A foreign `application_id`, a future `user_version`, and an empty file.
- A store built through `_migrate_v2` / backfill from a v3 fixture.

### 9.3 Conformance

The TS conformance tests read each scenario:

- R1 runs every read case against a **copy** of `store.sqlite3`, and asserts that the original's bytes are unchanged.
- R2 replays the scenario's write script from an empty store with the same injected clock and ids, then compares `dump.json` exactly.

### 9.4 Tolerances

Only the decay `new_value` may differ, by at most 1e-6 (H11). This is a numeric telemetry tolerance only. Everything else is compared exactly:

- scores as float64 bits;
- strings byte for byte;
- orders exactly;
- every discrete outcome that depends on decay: whether a maintenance event is emitted, the active/fading/dormant classification, wake or no-wake, and recall membership and order.

If a 1e-6 drift changes any discrete outcome, conformance fails, and the decision to pin a deterministic `pow` is revisited. A decay tolerance hit is reported in the output, never hidden.

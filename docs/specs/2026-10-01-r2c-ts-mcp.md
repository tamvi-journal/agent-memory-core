# R2c: TypeScript MCP server, raw boundary, connection lifecycle

Status: settled by Lam's review @ 1848941 (Q1–Q5 and F0–F7 applied). Author: Aux (leader). Builds on R0, R2a and R2b.

## 0. Goal, scope, dependency

R2c gives `@trajecta/identity` a stdio MCP server that can stand in for `trajecta_identity/mcp_server.py`, byte for byte on the wire. Python stays the oracle. The audit (§1) found that the Python server's raw boundary is undefined. R2c therefore first **defines** that boundary through oracle patches P6–P9, applied in both runtimes, and then ports it.

**F0 — dependency.** R2c is built from a `main` that already contains PR #16 (the R2b evidence-identity fix). The implementation branch and the corpus generator must start from that `main`. Building from 0f9943e would bring back the governance-identity divergence and stale provenance.

**In scope**
- The JSON-RPC 2.0 stdio loop (§2), with method envelopes (§3).
- Tool argument validation (§4), dispatch and results (§5).
- Tools and annotations (§6).
- The P9 bootstrap policy (§7) and the connection lifecycle (§8).
- Error-name mapping (§5.4).
- The TS entry point `node --experimental-strip-types node/src/mcp.ts --profile … --db …`, with no dependencies.

**Out of scope**
- **R2d (Q1 = yes):** the owner CLI in TS (TTY authority `approve-*`, `view`, `setup`, `plugin`, `decay`, `migrate`), and `doctor` without initializing.
- **R3:** cross-runtime runs, input fuzzing (including Lam's R2b note on present-null or non-string evidence metadata at the kernel), and the migration rehearsal.
- **R4:** installer and cutover.
- The gaps G1–G12 stay frozen, except that G6 is fixed on the MCP path by P9.

## 1. Oracle audit (Python server at main 0f9943e)

B1–B4 and B7 were reproduced by piping a transcript into `python -m trajecta_identity.mcp_server`.

| # | Finding | Effect today |
|---|---|---|
| B1 | stdin is decoded with `errors="strict"` in buffered chunks; the loop sits outside the try | one invalid UTF-8 byte kills the process, and earlier valid lines in the same chunk get no response |
| B2 | an exception in `handle` (a non-object request, non-object `params`) gets a traceback and no response | a request with an `id` hangs the client |
| B3 | `json.loads` failure takes the same path | no `-32700`; the client hangs |
| B4 | no argument validation | CPython text leaks (`KeyError: 'cue'`, `TypeError … unexpected keyword argument`); `"limit": "3"` is accepted |
| B5 | stdout `errors="replace"` combined with `ensure_ascii=False` | a lone surrogate comes out as `?` in Python but U+FFFD in TS |
| B6 | `initialize` echoes any `protocolVersion` | the server claims untested versions |
| B7 | `_ensure()` bootstraps an uninitialized store on the first call of any tool | a read call creates the store (G6) |
| B8 | `identity_retrieve` has `readOnlyHint: true`, but on v5 it tracks | the annotation is false |
| B9 | `_ready` is cached for the life of the process | a replaced or deleted store is never re-checked |
| B10 | `id: null` is treated as a notification; batches hit B2 | undefined |

## 2. Wire contract (P6, both runtimes)

### 2.1 Framing (F3)

stdin is read as **bytes**, never through a text decoder:
- frames are split on byte `0x0A` only;
- one final `0x0D` is removed from each frame;
- each frame is decoded as strict UTF-8 **independently**, so one bad frame cannot affect earlier or later frames in the same read chunk;
- at EOF, a final non-empty frame without a newline is processed once;
- a frame that is empty or all whitespace after Python `str.strip` of the decoded text is ignored;
- no other byte or character splits frames (lone `\r`, U+2028, U+0085).

### 2.2 Decode and parse

- Invalid UTF-8 in a frame gives `-32700` with `id: null`, and the server continues.
- Parsing is lossless (R0 F1): int and float stay distinct, and a repeated key keeps its first position and last value. JSON that does not parse gives `-32700` with `id: null`.

### 2.3 Request identity (F1, F2)

- **Notification or request depends only on whether the `id` member is present.**
  - With `id` **absent**, the message is a notification. It never gets a response, whatever the outcome. It is not dispatched to any tool, never bootstraps, and never writes. It is ignored once the envelope has parsed.
  - With `id` **present** (including `null`), the message is a request and gets **exactly one** response. A `method` starting with `notifications/` does not override this: with an `id` it is unsupported, and the response is `-32601`.
- **The id domain is closed.**
  - A request id is `null`, a string, or an **int token**.
  - An int is echoed losslessly, including values above 2^53, using its original token text.
  - A string is echoed exactly.
  - A float id (`1.0`), a boolean, an object or an array gives `-32600` with `id: null`.
- **Lone surrogates.**
  - A lone surrogate inside the id gives `-32600` with `id: null`, because it cannot be echoed safely.
  - A lone surrogate anywhere else, when the id is valid, gives `-32600` echoing that id.
  - A lone surrogate therefore never reaches the output (B5).

### 2.4 Envelope

- A top-level value that is not an object, including a batch array, gives `-32600` with `id: null` (B10: batches are unsupported, and the error says so).
- `jsonrpc` must be `"2.0"`, and `method` must be a string. Otherwise `-32600`, echoing a valid id.
- `params`, when present, must be an object. Otherwise `-32602`, echoing the id.

### 2.5 Error envelope (F6)

The exact shape, with insertion order `jsonrpc`, `id`, `error`, and inside it `code`, `message`, is:

`{"jsonrpc": "2.0", "id": <id-or-null>, "error": {"code": N, "message": "TEXT"}}`

The codes are closed:
- `-32700` `"Parse error"`
- `-32600` `"Invalid Request"`
- `-32601` `"Method not found"`
- `-32602` `"Invalid params"`

There is no `data` field; one would need a version bump.

### 2.6 Output

- Each response is one line: `json.dumps(response, ensure_ascii=False)` with the **default** separators `", "` and `": "`, no key sorting, and insertion order as specified. It is followed by `\n` and flushed.
- TS uses `pyJsonDumps`.
- Messages are processed strictly one at a time, in order. A response is written before the next frame is read.
- stdout carries only responses; details go to stderr.

## 3. Method envelopes (F4)

- **`initialize`:**
  - `params` may be absent or an object;
  - an absent `protocolVersion` means the latest supported version;
  - a present `protocolVersion` that is not a string gives `-32602`;
  - other fields (`clientInfo`, `capabilities`, …) are allowed and ignored.

  The result is:
  - `protocolVersion`: the client's value if it is in `SUPPORTED = ["2025-06-18", "2025-03-26", "2024-11-05"]`, else `"2025-06-18"` (B6);
  - `capabilities`, `serverInfo` and `instructions`: byte-identical to Python.

  `serverInfo.version` comes from **one pinned value** shared by both runtimes: `trajecta_identity.__version__` equals `node/package.json` `version`, and CI asserts it.
- **`ping`:** returns `{}`.
- **`tools/list`:** see §6.
- **`tools/call`:**
  - `params.name` is required and must be a string;
  - an absent `params.arguments` means `{}`;
  - a present `params.arguments` must be an object.

  A failure here gives `-32602` with the request id, because there is no valid invocation yet.

  A well-typed but **unknown** tool name keeps the current MCP behaviour: a success envelope with `isError: true` and the text `ValueError: unknown tool: <name>`.
- **Anything else:** `-32601`.

## 4. Tool arguments (P7)

- Every `tools/call` validates `arguments` against that tool's `inputSchema` **before any lifecycle `stat`, preflight or store access**. The JSON Schema subset is implemented directly in both runtimes, with no library:
  - `type`: object, string, integer, number, boolean, array;
  - `properties`, `required` and `additionalProperties: false`;
  - `minLength` and `maxLength`, in code points;
  - `minimum` and `maximum`;
  - `items` and `maxItems`;
  - `default`.
- **Recursion (F7).** `properties`, `additionalProperties`, `required` and `items` recurse into nested schemas, notably `vho_stack`. Nested failure paths use `/` (`vho_stack/runtime_architecture`, `follows/3`).
- **Kind rules follow the lossless AST:**
  - `integer` accepts only an int token (not `10.0` and not `"10"`);
  - `number` accepts an int or a float and **keeps the kind**, so R2b F1 holds end to end;
  - `boolean` accepts only `true` or `false`.
- **Free content.** `phase_context` is `{"type": "object"}` with free nested content. It passes on untouched, as the lossless AST.
- **Defaults (F7)** are applied to a **copy** of the validated arguments, after validation, in schema property order. They never mutate the parsed request AST.
- **Failure** produces a `tools/call` result (not a JSON-RPC error) with `isError: true` and the text `ValueError: invalid arguments for <tool>: <path>: <reason>`. The store is not touched. The first violation wins, in this order:
  1. an unknown key, in document order;
  2. a missing required key, in schema order;
  3. then, for each present key in schema order: type, then length or bounds, then items (recursively).

  The reasons come from the closed table in Appendix A.1.

## 5. Dispatch and results

### 5.1 Calls

The dispatch table is Python's `call_tool`, with the added `track` (§6). The TS methods are the public R2a and R2b methods, called with typed values. `budget` maps to `tokenBudget`.

### 5.2 Success

The result is `{"content": [{"type": "text", "text": T}], "structuredContent": S, "isError": false}`, where `T = json.dumps(result, ensure_ascii=False, default=str)` and `S` is the lossless re-parse of `T`.

### 5.3 Tool errors

- Any exception after validation gives `{"content": [{"type": "text", "text": "<PyName>: <message>"}], "isError": true}`.
- A bug in the server itself gives the same envelope with the text `RuntimeError: internal error`. Details go to stderr, and stdout still carries exactly one response.

### 5.4 Error-name map (TS → wire)

| TS | wire |
|---|---|
| `MigrationRequired` | `MigrationRequiredError` |
| `SchemaVersionError`, `IncompatibleJournalMode`, `PinnedRecordError`, `ValueError`, `RuntimeError`, `ReceiptNotFound`, `ReceiptIntegrityError`, `ProposalIntegrityError`, `ProposalDecided`, `StaleAuthority`, `WorkStoreError` | same name |
| migrate target or backup exists | `FileExistsError` (R2b carry; TS gains the class) |
| anything else | `RuntimeError: internal error` |

The corpus asserts every error text that a tool can reach.

## 6. Tools and annotations (P8)

- `tools/list` returns Python's tool order, descriptions and schemas byte for byte. Schema key order is built from ordered structures in Python order in both runtimes, never reconstructed from unordered maps.
- **`identity_retrieve` (Q2: one tool).**
  - It carries `readOnlyHint: false` and `idempotentHint: false`, and gains an optional `track: {"type": "boolean", "default": true}`.
  - The annotations describe the **worst-case** side effect (tracking on a ready v5 store).
  - `track: false` is always a pure read.
  - Any non-`ready` store is always a pure read (R2a/R2b).
  - The description adds: "Recall may update activation; pass track=false for a pure read."
- All other annotations are unchanged.

## 7. Bootstrap on an uninitialized store (P9, F5)

The bootstrap policy is an **explicit set**, and is never derived from annotations.
- **Never bootstrap:** `identity_status`, `identity_retrieve` (whatever `track` is), `identity_timeline` and `identity_core_proposals`. On an uninitialized store they answer from the empty state and create no file:
  - `identity_status` reports `store: "uninitialized"`;
  - `identity_retrieve` returns an empty packet;
  - `identity_timeline` returns `[]`;
  - `identity_core_proposals` returns `[]`.
- **May self-start (current behaviour kept):** the mutation tools (`identity_log_phase`, `identity_log_fact`, `identity_core_propose`, `identity_core_apply`, `identity_retract`, `identity_close_legacy_discussion`, `identity_close_loop`). They bootstrap an `uninitialized` store only **after** successful argument validation.
- There is no process-lifetime `_ready` cache (B9). The state is read per call.

## 8. Connection lifecycle (Q4 = B: no database cache across MCP calls)

- **At each `tools/call`:**
  1. after the envelope and argument validation, and before dispatch, close any connection left from a previous call;
  2. the first store operation in the call goes through the full preflight and post-open checks (R0 F2, R1);
  3. close again in a `finally` after dispatch.
- Within one call, TS may reuse its connection. No database state is kept across calls. This is not Python's "separate connection per internal method"; it is "nothing survives the call boundary".
- **Why not A:** a fingerprint of the main file (`dev`, `ino`, `size`, `mtimeNs`) does not detect a newly appeared `-wal` or `-shm` sidecar, and inode semantics vary across platforms. B is fail-closed by construction.
- The PR records p50 and p95 per call for B on the corpus store, for information only. It is not a correctness gate unless something extreme shows up.
- **Tests:**
  - a file swapped between calls is seen on the next call;
  - a file deleted between calls makes the next read `uninitialized`, and no file is recreated;
  - a foreign or future file swapped in fails closed;
  - a `-wal` sidecar that appears between calls fails closed;
  - no `-wal` or `-shm` is ever created.

## 9. Corpus and tests

- **`spec/golden-mcp-v1/`** is generated by Python from the patched oracle (built on post-#16 `main`, F0). Each scenario is:
  - `transcript.in`, raw bytes that may contain invalid UTF-8, CRLF or an unterminated final frame;
  - `expected.out`, the exact response bytes;
  - `store.sqlite3` and `dump.json`, or `absent` when no file must exist;
  - MANIFEST provenance.

  The generator drives a real `python -m trajecta_identity.mcp_server` subprocess, writing the transcript in **one** write, with injected clocks.
- **Required transcripts:**
  - **initialize:** each supported version; an unsupported version; an absent version; a non-string version (`-32602`); extra `clientInfo`/`capabilities` fields;
  - **basic methods:** ping; `tools/list`; an unknown method;
  - **notifications:** `tools/call` without an id (no output, no mutation, no file); `notifications/foo` **with** an id (one `-32601`);
  - **ids:** `0`, `9007199254740993`, `"x"`, `null`, `1.0`, `true`, `{}`, `[]`, `"\ud800"`; a lone surrogate elsewhere with a valid id;
  - **framing and parsing:**
    - one write containing a valid line, a bad-UTF-8 line and a valid line;
    - an unterminated final request;
    - CRLF lines; whitespace-only lines;
    - a parse error; a batch array; `jsonrpc` missing or wrong;
    - a non-object `params`;
  - **`tools/call` structure:** a missing or non-string `name`, a non-object `arguments` (`-32602`); an unknown tool (the `isError` text);
  - **arguments:**
    - every A.1 validation class, including `limit` as `10.0`, `"10"` and `true`;
    - a nested `vho_stack` failure path;
    - defaults applied without mutating the request;
    - `confidence` 1 vs 1.0 giving different fact keys;
  - **every tool:** a happy path, and every reachable typed error from §5.4, including legacy-v4 writes and read-only fallbacks;
  - **P9:** each never-bootstrap tool on a missing DB creates no file, including retrieve with `track` true **and** false; a mutation tool on a missing DB self-starts after valid arguments, and never after invalid ones;
  - **retrieve on ready v5:** `track` true and false.
- **TS replay:** spawn `node node/src/mcp.ts` with the same clocks, feed `transcript.in` in one write, and require `expected.out` byte for byte, plus the dump or absence.
- **Tests:** the lifecycle tests of §8, and a kill of the TS server mid-write `tools/call` followed by a reopen that shows no partial state.
- **CI:**
  - the Node job on 3 OSes runs the MCP replay;
  - the golden job regenerates `golden-mcp-v1` under 3 seeds in the pinned container, with a full diff including MANIFEST;
  - a check that the Python and Node versions are equal.

## Appendix A.1: validation reasons (closed table, both runtimes)

`unknown key` · `missing required key` · `expected <type>` · `shorter than <n> characters` · `longer than <n> characters` · `below minimum <n>` · `above maximum <n>` · `more than <n> items`

- `<type>` is one of `object`, `string`, `integer`, `number`, `boolean`, `array`.
- `<path>` is slash-separated from the arguments root (`limit`, `follows/3`, `vho_stack/runtime_architecture`).
- `<n>` is printed as written in the schema.
- An item type failure uses the item's path with `expected <type>`.

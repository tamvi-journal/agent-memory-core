# R2c: TypeScript MCP server, raw boundary, connection lifecycle

Status: draft for Lam review. Author: Aux (leader). Builds on R0, R2a and R2b (all settled; R2b closed by PR #16).

## 0. Goal and scope

R2c gives `@trajecta/identity` a stdio MCP server that can stand in for `trajecta_identity/mcp_server.py`, byte for byte on the wire. Python stays the oracle. The audit below found that the current Python server has no defined behaviour at its raw boundary: bad input can crash it, hang the client, or leak Python-specific error text. R2c therefore first **defines** the boundary (oracle patches P6–P9, in both runtimes), then ports it.

**In scope**
- The JSON-RPC 2.0 stdio loop: framing, decoding, lossless parse, dispatch, responses, and the error envelope.
- `tools/list`, including the tool schemas and annotations (readOnlyHint semantics, §5).
- Argument validation against each tool's `inputSchema` at the boundary (P7).
- `tools/call` dispatch to the R2a and R2b TS writers and readers.
- Connection lifecycle and revalidation for the TS store (§6).
- G6 for the MCP path: the server's `_ensure` must stop initializing a store on a read call (P9, see Q3).
- Mapping error class names so `isError` text is identical in both runtimes (§4.4).
- A TS entry point: `node --experimental-strip-types node/src/mcp.ts --profile … --db …`, with no dependencies.

**Out of scope**
- **R2d (proposed, Q1):** the owner CLI in TS (`approve-*` with the TTY guard, `view`, `setup`, `plugin`, `decay`, `migrate`).
- **R3:** cross-runtime runs on real OSes, input fuzzing (including Lam's R2b note on present-null or non-string evidence metadata at the kernel), and the migration rehearsal.
- **R4:** installer and cutover.
- The gaps G1–G12 stay frozen.

## 1. Oracle audit (current Python server, `trajecta_identity/mcp_server.py`)

B1–B4 and B7 were reproduced against the real server at main 0f9943e by piping a transcript into `python -m trajecta_identity.mcp_server`. For example, a `[1,2]` line and a malformed JSON line each produced a traceback and no response. A read call on a missing store created `s.sqlite3`. `"limit": "3"` was accepted. An unknown key returned CPython's `TypeError … unexpected keyword argument` text.


| # | Finding | Effect today |
|---|---|---|
| B1 | stdin is decoded with `errors="strict"`, and `for line in sys.stdin` sits **outside** the try | one invalid UTF-8 byte kills the server process. Reproduced: because decoding is buffered, even the **earlier valid lines in the same chunk get no response** |
| B2 | an exception in `handle` (a non-object request, non-object `params`, …) is logged to stderr and the loop continues **without a response** | a request with an `id` hangs the client forever |
| B3 | `json.loads` failure: the same path as B2 | no `-32700` parse error; the client hangs |
| B4 | there is **no argument validation**: `**fields` goes straight into the Python methods | unknown keys give `TypeError: IdentityMemory.log_phase() got an unexpected keyword argument 'x'`; a missing `cue` gives `KeyError: 'cue'`; `int(args.get("limit"))` accepts `"10"`, `10.7` and `true`. The text is CPython-specific, and TS cannot reproduce it. |
| B5 | stdout uses `errors="replace"` with `ensure_ascii=False` | a lone surrogate received as `"\ud800"` is echoed as `?`, whereas TS would write U+FFFD. The runtimes diverge. |
| B6 | `initialize` echoes whatever `protocolVersion` the client sends | the server claims versions it has never been tested against |
| B7 | `_ensure()` bootstraps an uninitialized store on the **first call of any tool**, including `identity_status` and `identity_retrieve` | a read call writes (G6) |
| B8 | `identity_retrieve` carries `readOnlyHint: true`, but on a v5 store it records access and applies recall (R2a carry) | the annotation lies to the client |
| B9 | `_ensure` caches `_ready` for the life of the process | if the store file is replaced or deleted, the server never re-checks it |
| B10 | `id: null` is treated as a notification; JSON-RPC batches (arrays) hit B2 | undefined behaviour |

## 2. Wire contract (both runtimes; oracle patch P6)

- **Framing.**
  - Input is UTF-8 bytes split on `\n`. One trailing `\r` is removed.
  - A line that is empty or all whitespace after Python `str.strip` is ignored.
  - No other separator (lone `\r`, U+2028, U+0085) splits lines.
- **Decoding.** Invalid UTF-8 on a line produces a `-32700` "Parse error" response with `id: null`. The server continues (B1).
- **Parsing.** Parsing is lossless (R0 F1): int and float stay distinct, and a repeated key keeps its first position and last value.
  - JSON that does not parse gives `-32700` with `id: null` (B3).
  - Any string containing a lone surrogate, in any key or value, is rejected as `-32600` "Invalid Request", with the `id` echoed when it can be read (B5).
- **Envelope.**
  - A top-level value that is not an object (including a batch array) gives `-32600` with `id: null` (B10: batches are not supported and are said so).
  - `jsonrpc` must be `"2.0"`.
  - `method` must be a string.
  - `params`, when present, must be an object.
  - A message with no `id` member is a notification and gets no response.
  - `id: null` is a request whose response carries `id: null`.
  - A string or integer `id` is echoed exactly, through the lossless AST.
- **Output.** One line per response: `json.dumps(response, ensure_ascii=False)`, with the **default** separators `", "` and `": "` and no key sorting, in insertion order as below, followed by `\n`, and flushed. TS uses `pyJsonDumps` from R2b. A lone surrogate cannot occur in output, because the parse rejected it.
- **Order.** Messages are processed strictly one at a time, in order. A response is written before the next line is read.
- **Methods.**
  - `initialize`: returns `protocolVersion` = the client's value if it is in `SUPPORTED = ["2025-06-18", "2025-03-26", "2024-11-05"]`, else `"2025-06-18"` (B6). It also returns `capabilities`, `serverInfo` (name, version from the package) and `instructions`, byte-identical to Python.
  - `ping`: returns `{}`.
  - `tools/list`: see §5.
  - `tools/call`: see §3 and §4.
  - `notifications/*`: no response.
  - Anything else: `-32601` "Method not found".

## 3. Arguments: validated at the boundary (oracle patch P7)

- Every `tools/call` validates `arguments` (absent means `{}`) against that tool's `inputSchema` **before** `_ensure` and before touching the store. The subset of JSON Schema in use is small and is implemented directly in both runtimes, with no library:
  - `type`: object, string, integer, number, boolean, array;
  - `properties`, `required` and `additionalProperties: false`;
  - `minLength` and `maxLength`, counted in **code points**;
  - `minimum` and `maximum`;
  - `items` and `maxItems`;
  - `default` (the dispatcher applies it).
- **Kind rules follow the lossless AST:**
  - `integer` accepts only an int token. Neither `10.0` nor `"10"` is accepted.
  - `number` accepts an int or a float, and **keeps the kind**, so R2b F1 holds end to end: `confidence: 1` and `confidence: 1.0` still produce different fact keys.
  - `boolean` accepts only `true` or `false`.
- **Failure.** The result is `isError: true`, and the text is exactly `ValueError: invalid arguments for <tool>: <path>: <reason>`. The first violation in a fixed order wins:
  1. an unknown key, in document order;
  2. a missing required key, in schema order;
  3. then each present key in schema order: type, then length or bounds, then items.

  The `<reason>` strings are a closed table in the spec appendix (A.1), shared by both runtimes. The store is not touched.
- **`phase_context`** stays `{"type": "object"}` with free content, passed on as the lossless AST.

## 4. Dispatch and results

### 4.1 Calls

This is the same table as Python `call_tool`. The TS methods are the public R2a and R2b methods, called with typed values. `identity_retrieve` maps `budget` to `tokenBudget`.

### 4.2 Success

The result is `{"content": [{"type": "text", "text": T}], "structuredContent": S, "isError": false}`, where `T = json.dumps(result, ensure_ascii=False, default=str)` and `S` is the lossless re-parse of `T`. A TS result is first converted to the same JSON AST as Python's return value. The corpus proves this per tool.

### 4.3 Tool errors

- Any exception raised after validation becomes `{"content": [{"type": "text", "text": "<PyName>: <message>"}], "isError": true}`.
- A failure of the server itself (a bug) is still a `tools/call` result with `isError: true` and the text `RuntimeError: internal error`. Details go to stderr only. A client with a pending `id` always gets exactly one response (B2).

### 4.4 Error-name map (TS → Python name on the wire)

| TS | wire |
|---|---|
| `MigrationRequired` | `MigrationRequiredError` |
| `SchemaVersionError`, `IncompatibleJournalMode`, `PinnedRecordError`, `ValueError`, `RuntimeError`, `ReceiptNotFound`, `ReceiptIntegrityError`, `ProposalIntegrityError`, `ProposalDecided`, `StaleAuthority`, `WorkStoreError` | same name |
| migrate "target or backup exists" | `FileExistsError` (R2b carry; TS gains the class) |
| anything else | `RuntimeError`, with the message `internal error` |

Messages must be byte-identical. The corpus asserts every error text that a tool can reach.

## 5. Tools and annotations (oracle patch P8, readOnlyHint)

- `tools/list` returns the tools in Python order, with byte-identical descriptions and schemas.
- **`identity_retrieve` (B8).** Proposal (Q2):
  - keep one tool;
  - set `readOnlyHint: false` and `idempotentHint: false`;
  - add an optional `track: boolean` (default `true`).

  With `track: false` the call is a pure read (R2a/R2b rules: a non-`ready` store is always a pure read). The description says that recall changes activation.
- **All other tools keep their annotations.** `identity_status`, `identity_timeline` and `identity_core_proposals` become truly read-only once P9 lands.

## 6. Connection lifecycle and revalidation (TS)

- **Python opens a connection per operation.** The TS store caches one `DatabaseSync` (`#database`). A cache that is never revalidated would keep reading an unlinked inode after the owner swaps a migrated copy into place (R0 E), and would miss a file that was deleted or replaced (B9).
- **Contract (Q4 proposes option A):**
  - **A — revalidate a cached connection per MCP call.** Before each call, `stat` the path and compare `(dev, ino, size, mtimeNs)` with the values recorded at open. On any difference, or if the file is missing, close, drop `_ready`, and reopen through the full R1 preflight (header bytes, then the post-open recheck). Writes already go through `BEGIN IMMEDIATE` on a fresh transaction, so this only affects reads that span calls.
  - **B — open per call,** exactly like Python. Simplest, and it costs one preflight and one open per call. Rejected for now only if a measurement shows it matters (the R2c PR reports p50 and p95 for both options on the corpus store).
- **Either way, the lifecycle tests must show:**
  - swapping the file between two calls is seen on the next call;
  - deleting the file makes the next read `uninitialized` (and never recreates it on a read, P9);
  - a foreign or future file swapped in fails closed;
  - no `-wal` or `-shm` sidecar ever appears.

## 7. G6 on the MCP path (oracle patch P9)

`IdentityServer._ensure` bootstraps only before a **write** tool (every tool with `readOnlyHint: false`), and only when the store is `uninitialized`. Read tools on an uninitialized store answer from the empty state:
- `identity_status` reports `store: "uninitialized"`;
- `identity_retrieve` returns an empty packet (the R2b fix);
- `identity_timeline` returns `[]`;
- `identity_core_proposals` returns `[]`.

This fixes G6 for the MCP surface in both runtimes. `validate_store` (doctor) stays frozen until R2d. If Lam prefers, it can be frozen as-is instead (Q3).

## 8. Corpus and tests

- **`spec/golden-mcp-v1/`** is generated by Python from the patched oracle. Each scenario is:
  - a `transcript.in` of raw bytes (it may contain invalid UTF-8 or CRLF);
  - an `expected.out` of the exact response bytes;
  - a `store.sqlite3` and `dump.json` after the run;
  - MANIFEST provenance, as in R2b.

  The generator pipes the bytes through a real `python -m trajecta_identity.mcp_server` subprocess, with injected clocks through the existing test seam.
- **Scenarios (minimum):**
  - initialize with each supported protocol version and one unsupported;
  - ping; tools/list; a notification; an unknown method;
  - a parse error; invalid UTF-8; a lone surrogate; a batch array; a non-object `params`; `id` values `0`, `"x"` and `null`;
  - every tool on a happy path;
  - every argument-validation class from A.1, including `limit: 10.0`, `"10"`, `true`, `confidence` 1 vs 1.0, an unknown key, and a missing required key;
  - every reachable typed error (from §4.4), including legacy-v4 writes and read-only fallbacks;
  - read tools on an uninitialized store (P9, no file created);
  - `identity_retrieve` with `track` true and false;
  - CRLF and whitespace-only lines.
- **TS replay:** spawn `node node/src/mcp.ts` with the same injected clocks, feed `transcript.in`, and require `expected.out` **byte for byte**, then compare the dump.
- **Lifecycle tests (TS):** §6.
- **Crash test:** kill the TS server mid-`tools/call` (a write); reopen; no partial state.
- **CI:** the Node job on 3 OSes runs the MCP replay. The golden job regenerates `golden-mcp-v1` under 3 seeds in the pinned container, with a full diff including MANIFEST.

- **Q2 — `identity_retrieve` annotations:** `readOnlyHint: false` plus an optional `track` (default true) (§5)? Or split it into `identity_recall` (tracks) and a pure `identity_retrieve`?

## Appendix A.1: validation reasons (closed table, both runtimes)

`unknown key` · `missing required key` · `expected <type>` · `shorter than <n> characters` · `longer than <n> characters` · `below minimum <n>` · `above maximum <n>` · `more than <n> items` · `item <i>: expected string`

The `<path>` is a JSON-pointer-like path from the arguments root, for example `limit` or `follows/3`. `<n>` is printed as in the schema.
